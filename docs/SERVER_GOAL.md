# 真实共享服务器世界：目标与当前证据

状态：**未完成**。旧 `link_world.h` / `link_session.h` 的私人世界隔离、怪物副本、
替身及血量转发不满足本目标。两个账号在相同地图、收到快照、入场握手成功、
显示相同血量，均不能证明真正进入同一个服务器世界。

## 必须完成的行为

房主拥有一个服务器世界。房主和房客的玩法请求都在该世界处理，实体、脚本、
怪物、生命值、死亡、复活及副本进度由同一份状态结算。房客进入时通过原生
场景卸载、读条和初始化流程，停止消费私人世界的玩法消息；离房、断线和失败
必须通过完整生命周期恢复私人世界。不能隐藏原有敌人来冒充隔离。

房主切换地图后，每个房客单独决定是否跟随。未同意者不能向新地图提交战斗
和交互请求；过期的同意不能用于后续地图或房间。玩家间传送也必须由服务器
检查目标世界和场景，进入对应场景后再确认落点。

原生 GUI、输入、动作平滑、玩家位置与距离显示保留。Minecraft 桥接暂不实现。
服务器与游戏适配器应分离，以便以后复用，不把跨游戏协议写入 EF 世界规则。

## 当前确认的入口（2026-10-10）

只读元数据与有界原生代码检查确认：

- `Network.Beyond.dll / Beyond.Network.HGNetSession.SendMessage(IMessage)` 是候选发送入口。
- `Network.Beyond.dll / Beyond.Network.NetBus.HandleMessage(NetResponse)` 是候选接收分发入口。
- 当前 `NetResponse` 为 32 字节值类型、8 字节对齐；`msgBody` 的装箱字段偏移为 24。
- `Gameplay.Beyond.dll / Beyond.Gameplay.GameplayNetwork` 存在
  `_Handle_ChangeSceneBegin`、`_Handle_EnterScene`、`_Handle_SelfSceneInfo` 等原生入口。
- 客户端场景通知包含独立 `scene_id` 与 `scene_num_id`；只匹配地图名称不等于共享世界。

`src/authority/link_transport_observer.cpp` 是开发诊断模块，只统计协议类型名称，
原样转发全部调用。它不保存消息内容、不改网络地址、不初始化或切换世界。
`authority_established` 永远为 false；统计到消息不能当作接管成功。
`tools/audit-native-protocol.py` 比较部分 protobuf 字段编号，也不认证完整协议兼容性。

## 可参考实现及限制

- [LR-S GitHub 源码](https://github.com/refield-industries/LR-S)，
  本地参考提交 `6204e1b6d64755913ae9381ba1c67a40da7edbf2`，声明客户端 1.0.14。
- [LR-S 上游源码](https://git.xeondev.com/LR/S)，
  本地参考提交 `936df33f69f7af2d2ddf52e650521e2667df0256`，声明客户端 1.5.3。
- [LR-C 客户端补丁](https://git.xeondev.com/LR/C) 展示本地服务器接入路线；
  包含固定地址补丁和全局请求重定向，未经当前客户端核对，未装载。

两个 LR-S 版本的 `Session.process` 均为每个登录连接创建独立 `logic.World`，
其 `World.level` 为会话私有，不能直接满足多人共享世界。最新参考的消息处理列表
也不能证明完整战斗、技能或副本逻辑已有服务器实现。源码在忽略的 `references/`
目录研究；未把其游戏数据表/资产加入发行包。

实机被动观察确认两端均经过上述收发入口。房主正常传送和战斗后观察到
`SC_SELF_SCENE_INFO`、实体进出视野通知、`SC_SCENE_TELEPORT` 与 111 条
`CS_BATTLE_OP` 调用；只保存类型计数，采集结束已关闭诊断钩子。

基于当前客户端元数据发现并修正参考 schema 缺失的 20 个战斗载荷 oneof 字段
（101–120）。部分其他版本的解析器把 `chapter_map_id` 定义为 17，当前客户端
实际为 4，不能直接复用。经本机只读检查，当前选择的场景/移动/战斗消息字段
编号与修正版一致；这仍不证明其他消息、原生世界适配器或完整结算已实现。

`server/src/Room.zig` 是新的服务器内存模型：一个房间共享一个实体存储，
对象 ID 由服务器分配，成员引导消息使用相同场景实例，禁止房客报告血量/死亡
充当结算。尚未接入真实游戏传输、完整场景初始化、战斗引擎、脚本和副本。
它的自动化测试属于服务器核心验证，不能算双 EF 实机验收。

当前服务器生成的 6 类合成协议消息已通过实机 `Google.Protobuf` 解析器校验，
包括战斗操作、场景切换、场景初始化和实体进视野。原生重编码保留字段语义；
加入队伍信息后的场景消息存在合法的字段顺序差异，并非逐字节相同。原生 getter
读取到正确的场景 ID、生命值和伤害载荷。测试对象没有交给游戏玩法处理器，
未修改游戏世界；不能把协议解析成功称为入场成功。

`server/src/SceneSession.zig` 管理完整入场顺序：场景切换通知、地图加载完成、
原生初始化数据以及对应世界/主控角色/私人消息源代次确认。加载地图后仍禁止
移动，避免在完整初始化之前假装已入场。实机适配器尚未接入该流程；它也不
提供战斗、脚本、副本或恢复私人世界的实现。

## 原生世界下行（2026-10-10，dev70–79，两台真实客户端）

方向：两名玩家都保持各自官方账号在线。房客在房间内时，其客户端的怪物
生命周期改由房主世界驱动：EF Link 用游戏自己的 protobuf 解析器构造标准
服务器消息，交给客户端自己的 `GameplayNetwork._Handle_ObjectEnterView` /
`_Handle_ObjectLeaveView`，由原生 `EntityManager` 流水线创建、生成和移除实体。
不再隐藏私人怪物、不再分配 `0xEF` 副本怪。没有任何消息发往任何服务器；
不做私服重定向或登录/加密绕过。

已确认的原生入口：`NetResponse`（32 字节：`headMsg`@0、`msgBody`@8、
`isPacked`@16、`recvTimestamp`@24）在游戏线程交给 `NetBus.HandleMessage`；
运行时 `Proto.SCMessageID`/`CSMessageID` 枚举给出当前消息号（如
`ScObjectEnterView=21`、`ScObjectLeaveView=22`、`CsBattleOp=901`）；
`ServerObjectEnterView → _MonstersEnterView → SyncServerCommonInfo →
SetupTemplate → SetupInLevelDataIfNeeded → MarkDataReady → Commit`。
关卡怪物的服务器实体 ID 等于关卡逻辑 ID，两个账号相同；关卡怪物位置取自
关卡数据；远处节点要等进入加载半径才生成实体（原生行为）。

实机结果：
- 离线客机：私人怪物经原生 `LEAVE_VIEW` 连数据层一起移除；同 ID 经原生
  `ENTER_VIEW` 重新生成为新实例（UID 129819 → 171187，`Started`）。
- 双端联机：房主不再隔离自己的怪物（房间怪物就是房主原生怪物，11 只）；
  房客以**房主的服务器 ID** 收到这 11 只并由原生流水线全部生成，自己账号的
  怪物原生离开视野；入场 `active`、无阻塞项。房客命中 13 次全部由房主采纳
  结算；房客侧 7 只怪物由房客原生 AI 驱动并攻击房客角色。
- 离房：房主怪物原生离开，房客自己的怪物原生恢复，期间暂存的官方视野消息
  按序重放。

官方上报隔离（`CS_BATTLE_OP`）：
- 首版把房主怪物的 `battle_inst_id` 设为怪物 ID，房客客户端随即把这些怪物的
  血量变化（1023 条 `entity_value_modify`）以相同 ID 报给**房客账号**的官方
  服务器——同 ID 即房客自己的怪物。已改为不下发 `battle_inst_id`（主体变为 0）。
- 每次快照重写血量产生的上报噪音（20 秒 1100 条）已消除：血量仅在变化时写入。
- 战斗操作带全局连续序号（`seq_id`，服务器还会 `SC_BATTLE_SYNC_SEQ_ID`），
  事后删包会留下空洞。改在源头：`BattleManager/ServerReporter.CreateServerOp<T>`
  （泛型共享实现，运行时按机器码唯一识别，两端均定位到同一 RVA）对房主怪物
  （本会话曾下发、`battleInstId=0`）和 EF Link 替身角色（`0xEF` ID）不创建操作，
  不消耗序号。房间内空闲时房客上报为 0；入场/离房的异步卸载仍有约 130–150 条
  主体为 0 的操作漏出，正在定位。
- 官方怪物的 `serverBattleInstId` 非零（房主侧实测 123459 等）。dev70–73 恢复
  私人怪物时未保留该值，导致房客测试账号在房主位置附近的若干私人史莱姆成为
  无战斗身份的本地副本，需重新登录或官方传送后由服务器重新下发。dev79 起
  缓存官方原始 `SCENE_MONSTER` 字节并原样重放，缺失时只恢复仍带战斗身份的记录。

事故：
- dev54 开发诊断在 RPC 线程调用原生施法导致客机崩溃（已改为游戏线程队列）。
- 18:03 房主进程在 dev77→dev79 热切换时崩溃，崩溃点为 Unity 卸载资源时的托管
  堆存活扫描（`il2cpp_unity_liveness_calculation_from_root`）。该进程一次会话
  内已装载 dev70–77 共 8 个版本。确切损坏来源未查明，责任在热切换方案；之后
  不再对房主热切换。

未完成：场景/地图切换仍用旧的客户端本地加载，而非原生 `SC_CHANGE_SCENE_BEGIN`/
`SC_SELF_SCENE_INFO` 流程；交互物、NPC、掉落、任务、Boss 与副本未接入；
怪物攻击结算在攻击对象一方（与官方客户端权威战斗一致，但不是单一服务器
结算）；入场/离房异步卸载的上报漏出；Zig 服务器核心尚未接入真实客户端。
